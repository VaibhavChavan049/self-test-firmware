# Self-Test Firmware  F28P650DK6PZP

This folder holds source only  there's no `.project`/`.ccsproject` checked
in here, because those must be generated by CCS on your machine (they
reference absolute toolchain paths). Since this environment can't run CCS
directly, the workflow is: build the project fresh in CCS, then copy the
`.c`/`.h` files from `src/` into it.

**Two folders, two purposes don't confuse them:**

- [`src/`](src/) — the **real firmware**. This is what goes in the CCS
  project you actually build and flash.
- [`reference/`](reference/) **scratch space** for TI-Rex examples you
  download (if the "Import to IDE" button in Resource Explorer isn't
  working, download the `.zip` instead and unzip it here see
  `reference/README.md`). Nothing in here is part of the final firmware;
  it's just somewhere to look at TI's example code and copy the correct
  driverlib calls out of.

## 1. Create the CCS project

1. Open CCS → **File → New → CCS Project**.
2. Target: `F28P650DK6PZP` (Piccolo/C2000 family pick the exact variant
   from the device list; CCS will offer to install the matching device
   support package if it's not already installed).
3. Project templates: pick **Empty Driverlib Project** (or the closest
   "empty project with driverlib" template offered for this device) this
   gives you the standard `device.h`, `driverlib.h`, linker command file,
   and startup code for free instead of writing them by hand.
4. Finish. You'll get a project with an auto-generated `main.c` delete
   its contents (or delete the file) and copy in the files from `src/`
   instead.

## 2. Add C2000Ware / driverlib

C2000Ware is already installed locally at `~/ti/C2000Ware_26_01_00_00/`
(installed via Resource Explorer's "Download and Install", F28P65x
component only). If the empty-driverlib template didn't already pull it
in as a dependency: **Project → Add Files** → point at
`~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/driverlib`. Everything in
`src/` is written against standard C2000Ware driverlib calls (`GPIO_*`,
`ADC_*`, `SCI_*`) and has been checked against this exact install.

## 3. Copy in the files

Copy every file under [`src/`](src/) into your CCS project's source
folder:

- `main.c` — entry point, bring-up, command loop
- `test_config.h` **the list of what gets tested.** Add a new
  parameter here; nothing else needs to change.
- `self_test.c` / `self_test.h` — orchestrator, walks `test_config.h`,
  dispatches to the right test module, reports over UART
- `gpio_test.c` / `.h` GPIO input/output test logic
- `adc_test.c` / `.h` ADC channel test logic
- `led_test.c` / `.h` LED test logic (electrically a GPIO output;
  see file header for why it's a separate module anyway)
- `uart_comm.c` / `.h` the only file that talks to the SCI peripheral;
  implements the protocol in [`../docs/protocol.md`](../docs/protocol.md)

## 4. What's confirmed vs. still open

All driverlib calls in `src/` have been checked against the real
C2000Ware 26.01.00.00 install (`~/ti/C2000Ware_26_01_00_00/`) headers
(`gpio.h`, `adc.h`, `uart.h`, `pin_map.h`, `hw_memmap.h`) and the
reference examples (`gpio_ex2_toggle.c`, `adc_ex1_soc_software.c`,
`uart_ex1_echoback.c`). Function names, signatures, and base-address
macros used in `gpio_test.c`, `adc_test.c`, and `uart_comm.c` are real,
not guesses — including two corrections that came out of checking:

- **GPIO70/71 (DBG_UART) mux to the UART peripheral, not SCI.** This
  device has two separate serial blocks - legacy SCI (`sci.h`) and a
  newer, separate UART block (`uart.h`). GPIO70/71 support pin-mux
  options for both, but the board's own pinmux planning sheet marks the
  selected mode as `UARTB` (`Used By: uartDBG`). `uart_comm.c` was
  rewritten to use `UARTB_BASE` + `UART_*` calls accordingly (an earlier
  version used `SCIB_BASE`, which would not have worked).
- **FAULT (GPIO86) and Vsens_AD (B3) removed from `test_config.h`.** The
  board's own pin function list marks both as not connected to anything
  on this board revision ("does not go anywhere" / "goes nowhere").
  Testing a floating pin produces noise, not a real result, so both were
  dropped rather than tested. Add them back if a later board rev wires
  them up.
- **LED_YELLOW corrected to GPIO61** (was GPIO60 from an earlier
  schematic read the board's text pin-function list is the more
  reliable source and says GPIO61).

Still open (won't block a first build, only matters once running on real
hardware):

- `test_config.h` button/fault-signal `expectedValue` polarity
  (active-low assumed) and ADC expected ranges (currently full 0-4095,
  i.e. "conversion works" not "sensor reading is sane") see that file's
  TODO block.
- `adc_test.c` sample window (cycles) is a reasonable default, not
  tuned per sensor's source impedance; only matters if readings look
  noisy once on hardware.
- Whichever CCS project template/toolchain version is actually installed
  on your machine might use slightly different linker command file names
  than what's referenced in the example `.syscfg`s not a `src/` concern,
  just something CCS's own project wizard handles when you create the
  project (step 1).

## Where the reference examples actually are

C2000Ware is installed locally, so the reference examples are plain files
on disk no need to re-browse Resource Explorer or the `reference/`
folder workflow for these three, they're already read and accounted for:

```
~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/examples/c28x/gpio/gpio_ex2_toggle.c
~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/examples/c28x/adc/adc_ex1_soc_software.c
~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/examples/c28x/sci/sci_ex3_echoback.c
```

Headers worth knowing about if you need to check anything else yourself:

- `~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/driverlib/gpio.h` GPIO API
- `~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/driverlib/adc.h` ADC API
- `~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/driverlib/pin_map.h` pin
  → peripheral-function mux macros (e.g. `GPIO_70_SCIB_TX`)
- `~/ti/C2000Ware_26_01_00_00/driverlib/f28p65x/driverlib/inc/hw_memmap.h`
  module base addresses (`SCIB_BASE`, `ADCA_BASE`, etc.)
- `~/ti/C2000Ware_26_01_00_00/device_support/f28p65x/common/include/device.h`
  and `.../common/source/device.c` what `Device_init()`/`Device_initGPIO()`
  actually do

## Protocol

Firmware ↔ GUI communication is a plain-ASCII line protocol see
[`../docs/protocol.md`](../docs/protocol.md). `uart_comm.c` is the only
file responsible for emitting it correctly; every other file just calls
`UART_send*()`.
